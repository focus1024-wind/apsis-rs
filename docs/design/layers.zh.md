# 分层边界

[English](./layers.md) | 简体中文

本文件记录本 crate 的分层规则，以及为什么某些跨层引用是允许的。README 的
"分层"一节是规则本身，这里是它的判定标准与边界情况。

## 规则

层自左向右排列：

```text
foundation -> physics -> orbit -> rf -> network -> ops -> sim
```

一条引用边从模块 A 指向模块 B。把 A 所在的层与 B 所在的层分别映射为
下标，规则是：

```text
index(B) <= index(A)     允许
index(B) >  index(A)     违规（反向引用）
```

即**只能向左引用，不能向右引用**。`scripts/check-layers.sh` 对本 crate 的
每个模块目录执行这条判定，CI 会运行它。

## 允许跨层

规则只看方向，不看距离。从 `network` 直接引用 `orbit` 是允许的，尽管中间
隔着 `rf`：`orbit` 在 `network` 左边，方向正确。

允许向左跨层是有意的。若强制只能引用紧邻的左层，会产生两类问题：

- **中转类型不存在。** 把 `orbit` 层的位置传给 `network` 层时，`rf` 层并
  非必然提供一个承载该位置的类型。强行要求经过 `rf` 只会制造只是转发的
  空壳类型。
- **无谓的耦合。** `network` 的星座计算需要 `apsis_kepler` 的开普勒要素，
  它并不需要 `rf`。若禁止跨层，`network` 就得引用 `rf` 只为拿到一个它不
  使用的类型。

因此规则约束的是**方向**，因为方向才对应真正的分层语义：上层的概念可以
引用下层的概念，反之则说明分层错了。

## 全局基准

`apsis_core`（通用错误、常量、单位标记）与 `apsis_math`（`Vec3`、
`Mat3`、`Quat`）被各层共用。它们本身在 `foundation` 中，所以"只向左引用"
已经允许任何层使用它们，无需特例。

这与"层内基准"不同：`apsis_core` 也是 `foundation` 内的基准，但它的可用
范围是整个 crate，而不只是同层。

**只有真正使用的模块才引用。** `apsis_core` 与 `apsis_math` 可以被任何
模块引用，但一个不使用它们的模块不应导入它们：未使用的导入会拖慢编译、
让分层检查产生噪声，并让"谁依赖什么"失真。需要时再加，是一条随时可走的
单行改动。`scripts/check-layers.sh` 报告的边数因此是真实的使用关系，而
不是一份预留清单。

## 层内门面

每层以一个门面模块作为整合点：

| 层 | 门面 |
| --- | --- |
| orbit | `apsis_orbit` |
| rf | `apsis_rf` |
| sim | `apsis_sim` |
| 对外 | crate 根，即 `apsis` |

门面把同层的能力组合成少量类型，并再导出同层的其余模块。`foundation`、
`physics`、`network`、`ops` 没有单独门面：它们的模块各自独立有用，且
crate 根会把它们一并再导出。

## 边界情况

- **crate 根不在层序列中。** 它再导出全部层，因为它就是出口。
  `scripts/check-layers.sh` 通过层目录名判定，`src/lib.rs` 不是
  `src/<layer>/<module>` 形状，因此被跳过。
- **测试也计入检查。** 一条测试里的反向引用同样说明分层错了，应当修正
  代码而不是放宽测试。
- **再导出不构成新引用。** crate 根把 `apsis_orbit` 再导出，是门面行为，
  不是某层对 `orbit` 的引用。

## 检查

```bash
bash scripts/check-layers.sh
```

脚本输出检查过的引用边数，并在发现反向引用时逐条列出后以退出码 1 结束。
边数随代码变化，因此此处不写死；运行脚本得到的数字才是当前的真实关系。
